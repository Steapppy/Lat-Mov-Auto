Executive Summary

The current authentication module provides a solid proof-of-concept: it performs a service sweep across WinRM, SMB, and WMI based on prior recon data and supports targeted execution via a configurable command flag (-c). This proposal outlines four incremental enhancements that would elevate the module from a demonstration tool to a production-grade lateral movement engine, with direct traceability to real-world adversary techniques (MITRE ATT&CK T1550, T1110).

Each feature is described with its technical implementation approach, its contribution to the overall framework, and an estimated development effort. Features are ordered by implementation priority: the first three build on each other and are low-risk; the fourth is the most technically complex but the highest-value for demonstrating advanced credential abuse.

Proposed Features

1
Auto-Store Successful Authentication Results
Low Complexity

Description

When the authentication sweep or a forced-service authentication succeeds, the working credential set is automatically persisted to the framework's credentials database, tagged with the target host and the services it grants access to. Currently, successful results are only printed to the operator's terminal and are lost when the session ends.

Technical Implementation

This is an operator-side change only — no agent recompilation required. After _do_auth_sweep() completes, the operator CLI parses the per-service results, identifies successes, and calls the existing POST /credentials server endpoint with the username, secret, type (plaintext), and source host. An additional services field in the payload records which access paths are confirmed open. 

# Pseudocode — operator side only
if sweep_result[svc] == SUCCESS:
    POST /credentials {
        username:    "admin",
        secret:      "Password123",
        cred_type:   "plaintext",
        source_host: "10.0.2.5"
    }

Value to the Framework

  • Closes the feedback loop between the authentication and credential management modules.
  • Credentials accumulate passively — operators can revisit them at any point with credentials.
  • Enables downstream features (Features 2 & 3) that rely on a populated credential store.
  • Aligns with real-world C2 behaviour where successful logins are automatically loot.

Estimated Effort

~1 hour. Pure operator CLI change, ~30 lines. No server or agent modifications.

2
Credential Spraying from the Database
Low Complexity

Description

A new spray <target_ip> operator command (or authenticate --spray <target_ip>) that retrieves all stored credentials from the framework database and sequentially attempts each one against the target, reporting which credential and service combination succeeds. This directly reflects the real-world attacker workflow of reusing harvested credentials across multiple hosts.

Technical Implementation

Operator-side only. The command fetches GET /credentials, iterates over each stored credential, and calls _do_auth_sweep() (or a single-service variant for speed) for each. Results are aggregated into a compact matrix: credential × service. 

# New operator command
spray 10.0.2.5

# Output
Spraying 4 credential(s) against 10.0.2.5 ...
  [+] admin / Password123    →  WINRM ✓  SMB ✓  WMI ✗
  [-] svc_backup / hunter2   →  all failed
  [+] jdoe / Summer2024!     →  WINRM ✓  SMB ✗  WMI ✗
  [-] guest / (empty)        →  all failed
2/4 credentials valid on this host.

Value to the Framework

  • Makes the credential store actionable — loot collected during one phase of the engagement is immediately usable in the next.
  • Surfaces credential reuse across the environment with a single command.
  • Directly maps to MITRE ATT&CK T1110.003 (Credential Stuffing) and T1078 (Valid Accounts).
  • No agent changes, no server changes — maximum value for minimum risk.

Estimated Effort

~2–3 hours. New operator command + result aggregation display. Reuses all existing infrastructure.

3
Multi-Target Credential Spray
Low Complexity

Description

The inverse of Feature 2: given a single credential set, attempt authentication against every host in the framework's host database that has at least one lateral movement port open. This enables operators to quickly determine the blast radius of a compromised account across the entire known network.

Technical Implementation

Operator-side only. A new flag --all on the authenticate command (or a dedicated spray-all command) fetches GET /hosts, filters for hosts with ports 445, 5985, 5986, or 135 open, and runs _do_auth_sweep() against each. Results are printed as a host-by-host table and, combined with Feature 1, automatically stored for any successes. 

# Authenticate one credential set against all known hosts
authenticate -u admin -p Password123 --all

# Output (summary)
Sweeping 6 reachable host(s) with 1 credential set ...
  10.0.2.4   →  WINRM ✓  SMB ✓  WMI ✓
  10.0.2.5   →  SMB ✓    WMI ✗
  10.0.2.10  →  all failed
  10.0.2.15  →  WINRM ✓
  ...
3/6 hosts accessible with admin / Password123.

Value to the Framework

  • Immediately answers the critical post-compromise question: where can this account go?
  • Enables automated attack path discovery — combined with BloodHound data, this forms the foundation for a full graph-based lateral movement engine.
  • Maps to MITRE ATT&CK T1021 (Remote Services) and demonstrates genuine understanding of network-wide credential reuse.

Estimated Effort

~2 hours. Operator-side loop + display table. No agent or server changes needed.

4
Pass-the-Hash Authentication
Medium Complexity

Description

Support NTLM hash-based authentication in addition to plaintext passwords, via a new -H <NTLM_hash> flag. Pass-the-Hash (PtH) is one of the most widely used lateral movement techniques in real-world engagements: it allows an attacker to authenticate using a credential hash harvested from memory (e.g. via Mimikatz or secretsdump) without ever knowing the plaintext password.

Technical Implementation

Native Windows commands (winrs, net use, wmic) do not natively accept NTLM hashes. The recommended implementation strategy uses a tool-delivery model consistent with the framework's existing architecture:

  1. The operator uploads Invoke-TheHash.ps1 (or a compiled equivalent) to the server's /files/ directory once.
  2. When a PtH authentication task is queued, the agent downloads the tool to %TEMP% (reusing the existing DownloadTool() helper), executes the appropriate function with the hash, and returns output.
  3. The operator CLI detects -H, sets cred_type = "ntlm", and formats the instruction as user|hash|target|service|ntlm. 
# Operator usage
authenticate -u administrator -H aad3b435b51404ee:31d6cfe0d16ae931 -s winrm 10.0.2.5

# Agent executes (PowerShell via Invoke-TheHash)
Invoke-WMIExec -Target 10.0.2.5 -Username administrator `
    -Hash 31d6cfe0d16ae931b73c59d7e0c089c0 -Command "whoami"

Value to the Framework

  • Enables a complete attack chain: secretsdump → harvest NTLM hash → PtH to lateral move — all within the same framework.
  • Demonstrates credential abuse without plaintext secrets, which is the realistic scenario in hardened environments where LSASS protections or password complexity policies are in place.
  • Directly maps to MITRE ATT&CK T1550.002 (Use Alternate Authentication Material: Pass the Hash).
  • The tool-delivery approach keeps the agent lightweight and avoids embedding offensive tooling in the compiled binary.

Estimated Effort

~4–6 hours. Requires operator CLI changes (-H parsing), a new task instruction format, and client-side tool download + execution logic. Dependent on availability of a suitable PtH tool in /files/.

Summary & Priority Matrix

The table below summarises the four features by complexity, estimated effort, and components affected. Features 1–3 can be delivered incrementally with no agent recompilation; Feature 4 requires a coordinated agent and operator update.

# Feature Complexity Effort Agent Change ATT&CK Mapping
1 Auto-Store Auth Results Low ~1 h None T1078
2 Credential Spray from DB Low ~2–3 h None T1110.003
3 Multi-Target Spray Low ~2 h None T1021, T1078
4 Pass-the-Hash Medium ~4–6 h Yes T1550.002

Recommended Approach

The recommended delivery order is 1 → 2 → 3 → 4. Features 1, 2, and 3 are additive, low-risk, and each builds on the previous: auto-storing results (1) populates the database that spraying (2, 3) relies on. Together they create a coherent harvest → store → reuse workflow that demonstrates the full value of maintaining a persistent credential store across an engagement.

Feature 4 (Pass-the-Hash) is recommended as a second milestone once the spraying features are validated. It requires a one-time tool upload to the server and a coordinated agent recompilation, but it significantly elevates the technical depth of the framework and is the most direct demonstration of real-world credential abuse techniques.

All four features are achievable within the current architecture with no breaking changes to existing functionality.
